Milestone 1

1The data and the one split

Where the 6,942 photos came from, how they were cleaned, and why the split was made once, before anything else, and never changed.

1. The dataset

The course dataset has 7,343 image files in 73 object folders. Each object was photographed about a hundred times by one student, mostly in their own rooms. That makes the photos realistic, but it also builds in the dataset's main bias: an object and its background travel together, so a model can learn the room instead of the object. The project measured this in every milestone.

2. Cleaning, with two simple rules

  • Background-only photos (the empty room) were removed by file name: 385 of them. Untagged ones stayed: five OBJ004 photos show only the room, and Milestone 2 removed them by eye.
  • Exact duplicates were found by comparing file bytes (MD5): 16 copies removed. A re-saved copy or a burst shot is not caught this way; 99 test photos have a near-twin in training, which is why Milestone 1 also reports a hard subset of the 943 test photos without one.

3. One split, made first

The 6,942 photos were split 70/15/15, balanced per object, with a fixed seed (42), so the shuffle is identical whenever it is rerun. The split was made before any box or model existed and kept for the whole project: a test photo in Milestone 1 is still a test photo in Milestone 4. That single decision is what makes every later comparison fair.

4. Are the folder labels right?

A logistic regression on frozen ConvNeXt-Tiny features, cross-validated in five folds, agreed with the folder label for 98.3% of photos in the fully logged run (97.9% in the submitted study): a high level for 73 classes, with no sign of systematically mislabelled folders.

One photo is a phone screenshot with personal details. It was blurred in every figure, together with twelve images an automatic check flagged as possibly showing a phone screen, and later removed from all detection data.

2Five networks, one recipe

Why five networks were trained the same way, what transfer learning means, and what the clean test accuracy did and did not show.

1. A fair comparison

A custom VGG-style CNN with ten convolutional layers was trained from scratch and compared with four networks pretrained on ImageNet: ResNet-50, EfficientNet-B0, ConvNeXt-Tiny and DenseNet-121. All five used one shared recipe, so any difference reflects the architecture rather than a trick given to one model: AdamW, a new output layer learning 3 to 10 times faster than the pretrained layers, a warm-up then a cosine decay of the learning rate, label smoothing 0.1, class weights, mixed precision and early stopping on validation macro-F1.

3. Transfer learning decides first

Every pretrained network beat the scratch CNN by about ten points. A network pretrained on ImageNet has already learned edges, textures and shapes from a million photos; training only has to teach it which combinations mean this keyboard or that tissue box. Like a trained chef learning a new recipe, it starts far ahead of someone who has never cooked.

4. What clean accuracy could not decide

Among the four pretrained models, the differences on clean photos lie inside each other's intervals, and McNemar's test (which compares two models on the same photos, using only the photos where exactly one is right) confirms that ConvNeXt-Tiny is not significantly better there. Choosing by clean accuracy would have been choosing by noise. The next lesson shows what decided instead.

Augmentation also mattered. In the fully logged replication, the same ConvNeXt-Tiny with only basic augmentation lost 20 points on low-quality photos and 11 on small ones: evidence that the richer recipe was worth it.

3Choosing for robustness

How a rule written before the test chose the model that holds up best when photos are small, cropped, hidden or poor.

1. Four ways real photos go wrong

Each validation and test photo was also tested under four simulated problems: small (the object at half size on a blurred canvas), cropped (a 70% window), occluded (a grey box over a quarter of the image) and low quality (four times smaller, darker, heavily compressed).

2. The rule, fixed in advance

Keep the models within 0.5 points of the best validation F1, then choose the most robust on the validation versions of the four problems. The test set played no part in the choice.

3. What it chose

clean test accuracymean of the four problems (test)the selected model

ConvNeXt-Tiny led on validation (83.98%) and, as the chart shows, on test too: the most robust model under every problem. Low-quality photos were the hardest condition for every model (best 51.7%), a weakness the project met again in every milestone.

4What the classifier looks at

Where the networks look in a photo, what they do when there is no object at all, and what could not be re-verified.

1. Heat maps

Grad-CAM colours each part of a photo by how much it pushed the network towards its answer. For clearly visible objects the pretrained networks focus tightly on the object itself.

2. The background test

A sharper question: shown a photo of an empty room, which object does the model name? Every model named the photographer's own object for about a third of the empty scenes: ConvNeXt-Tiny 35.7%, against 1.37% by chance (1 in 73). Its confidence was low (0.36 against 0.89 on real photos), so the room is a weak, secondary cue. A classifier must always name something; this finding became the thread that Milestone 3 later repaired.

3. The eight errors

On the 1,042 test photos ConvNeXt-Tiny made 8 errors: 4 photos with several objects in view, 2 look-alikes, 1 very small object and 1 screenshot.

4. What could not be re-verified

The submitted study ran in Google Colab and its notebook was saved without outputs, so its numbers come from the Milestone 1 report alone. A local run with the same split, recipe and rule is fully logged and reached the same conclusion (ConvNeXt-Tiny, 99.42%). The submitted 99.23% stays the official result; the local run is the replication.

A small puzzle, honestly recorded: the background test used 378 photos although 385 were removed. No file records why; most likely the 385 contain seven byte-identical copies (385 − 7 = 378) that the Colab notebook removed before filtering the backgrounds.

Milestone 2

5The problem

What Milestone 2 asked, and why it was much harder than Milestone 1.

Milestone 1 trained a classifier: one photo in, the name of its single object out. Milestone 2 asks for object detection: for every object in an image, its Object ID and a bounding box, the smallest rectangle around it, written as four numbers (left, top, right, bottom in pixels).

Why it was harder

  • No boxes existed. The course dataset only said which object each photo shows. A detector needs boxes twice: to learn from, and to be graded against. Making about 7,000 boxes became the largest part of the project.
  • Finding is harder than naming. Many objects are small, far away or in clutter, and several look alike (watches, wallets, rackets).
  • The multi-object images had to be built. The milestone defines them as grids of 224 × 224 photos, from 2x2 (4 objects) to 5x5 (25 objects).

The data

Milestone 1's cleaning turned 7,343 files into 6,942 usable photos of 73 objects, removing 385 background-only photos and exact duplicates. They are split 70/15/15 per object with a fixed seed (42): 4,859 training, 1,041 validation and 1,042 test photos. A grid is only ever built from photos of one split.

6Making the boxes

How about 7,000 boxes were made without drawing them all by hand: three box-drawers that fail in different ways, and a vote.

Three rules set first

  • Independence: trust a box only when methods that fail differently agree on it.
  • People check the test boxes: the test set produces every reported number.
  • Measure, don't assume: measure how often the machine boxes are right.

The three box-drawers

DrawerHow it worksWhat happened
OWLv2, text promptan open-vocabulary detector that looks for whatever a sentence describes; given the object's name, its highest-scoring box is keptrun on all 6,936 photos; 5,570 usable boxes (80.3%)
OWLv2, image promptthe same model, shown 3 example crops per object (hand-drawn for 7 objects) and asked to find something similarits boxes often covered floor, bed or table; it agreed with the text boxes on only 47.9% of photos, so it was demoted to one vote
YOLO helper (YOLO26-s)trained by the project on 3,915 usable text-prompt boxes from training photos only, 40 epochs; then run on every photovalidation mAP@0.5 = 0.950 on single photos; never saw a validation or test photo, so its opinion there is independent

The other 940 boxed training photos (4,855 − 3,915; 4 of the 4,859 training photos were excluded) were not used to teach the helper, but still received a helper box and an image-prompt box and went through the vote. Only the helper was trained by the project; OWLv2 is ready-made.

The vote

Two boxes "agree" when their IoU is at least 0.70; the helper may vote only when its confidence is at least 0.25, and every voting box must cover between 1% and 97% of the photo. All three agree: strong (3,172 photos). Exactly two agree: auto (2,935). Otherwise the photo goes to review by a person: 794 where no two boxes agree, and 35 where the helper confidently sees another object (829 in all). Strong and auto boxes (6,107) were accepted, because two methods with different blind spots rarely make the same mistake in the same place.

8The label audit

How five objects turned out to have been boxed in two different ways, and why fixing them mattered more than changing the model.

Why inconsistent boxes are so harmful

If the tissue box is boxed around only the paper in some photos and around the whole box in others, the model receives contradictory answers and hedges, and even a perfect prediction is marked wrong against half the answer key, because the two rectangles barely overlap (IoU about 0.30). It is like grading with two answer keys mixed together.

How they were found and fixed

The trained models scored a few objects far below the rest; looking at every box of those objects side by side showed two ways of boxing. One rule was written per object, and every photo of it was re-checked in every split. The fixes came in two rounds: the sneaker rule first, then four more.

9Building the grids

When and how the grid images were built, and what that does and does not add to the dataset.

When and how

After the split and after every photo had its box. Each photo is 224 × 224 px and fills one cell: 2x2 = 448 px, 3x3 = 672, 4x4 = 896, 5x4 = 1,120 × 896, 5x5 = 1,120 px. The box moves with its photo: a box from (50, 30) to (180, 200), placed in column 2, row 1 (counting from 0), shifts by 448 across and 224 down to (498, 254)–(628, 424).

Three kinds of grids

SetBuiltContents
Validationonce, fixed68 grids, 972 objects, every validation photo once

The 16 test 2x2 grids hold 61 objects plus 3 empty background filler cells, so the 72 test grids contain exactly 1,041 objects. Later counts of 1,044 and 1,048 belong to Milestone 3's corrected answer keys (second objects added).

Did it increase the dataset?

The number of training images went up, but not the number of different photos: still the same training photos, each appearing in about 4 of the 1,500 images, in different grids, neighbours and positions. It is like reshuffling one deck of cards: no new cards, many new hands. On top of that, Ultralytics changes every image each time it is loaded (flips, colour, mosaic, small zoom and shift), so no epoch sees exactly the same pictures.

10Training, validation and test

The three groups of photos and their three different jobs.

GroupAnalogyJobPhotos
Trainingtextbook and homeworkthe model learns from these4,859
Validationpractice examsused to make every decision1,041
Testthe final examused once, to report the result1,042 (1,041 used)
  • Training: look at a batch, measure the error (the loss), adjust the weights. Scores on training photos mean nothing, because a model can memorise them (overfitting).
  • Validation: after every epoch the model is scored but learns nothing. The score keeps the best epoch (best.pt), stops training when it is flat (12 epochs in Milestone 2), picks between runs and picks the settings. Because many choices are made by looking at it, the chosen model's validation score is slightly optimistic: 0.972 against 0.947 on test.
  • Test: scored once, after every choice was made, on person-checked boxes.

Honesty comes from three habits: split by photo before anything else, build grids within one split only, and let the test set decide nothing. Milestone 3 later found 183 near-duplicate pairs across splits and removed 41 training and validation copies.

Batch size 4

The model looks at 4 images, scores itself once on their average error and adjusts its weights once: 1,500 ÷ 4 = 375 adjustments per epoch. One image at a time would make each adjustment jumpy; all 1,500 at once would not fit in memory. At 1,120 px only 4 fitted in the laptop GPU's 8 GB. Run 2 made 60 × 375 = 22,500 adjustments; the selected model saw 90 epochs × 1,500 = 135,000 training images in total.

YOLO label files

YOLO keeps one text file per image, not one per object: grid_0001.jpg has grid_0001.txt, with one line per object: the class number and the box's centre x, centre y, width and height as fractions of the image size. The 73 class names are listed once in the dataset file. The box (498, 254)–(628, 424) in a 1,120-px grid is written as 0.5027 0.3027 0.1161 0.1518. The source of truth is boxes_master.csv (one row per photo, in the photo's own coordinates); the label files are generated from it when the grids are built.

11The five model runs

How the detector was trained, improved and chosen: the data it learned from, the two layers of augmentation, the settings, every run with its scores, the two rounds of data fixes, and how the winner was picked. Numbers come from the project's run records; lesson 7 shows how every photo got its box.

data: what the model learns froma trained modelsetup and decisions

The ideas behind the diagram

  • Two candidates. YOLOv8-s is the model named in the course brief; YOLO26-s is the newest detector from Ultralytics. Comparing them tests whether a newer architecture helps instead of assuming it. Both are small (s) models: at 1,120 px only a batch of 4 fits in the laptop GPU's 8 GB.
  • COCO pretraining. Both start from weights learnt on about 118,000 everyday photos in 80 categories, so they already recognise edges, shapes and "objectness".
  • Input size 1,120 px. A 5x5 grid is 5 × 224 = 1,120 px, so every photo keeps its native 224 pixels.
  • Batch 4. The model predicts on 4 images, measures its error, and adjusts its weights once: 375 adjustments per epoch of 1,500 images.
  • Fine-tuning. "+ 15 epochs" continues from the previous run's weights on improved data instead of starting again.
  • Two layers of augmentation. The 1,500 training images are built once and fixed: which photos sit in which grid, the grid sizes, the look-alike groups, the single photos and the baked-in degradations. Ultralytics then changes each image every time it is loaded (flips, colour, mosaic, small zoom and shift), so no epoch sees exactly the same pictures. Each training photo appears in about 4 of the 1,500 images.
  • Choosing on validation. The winner, the threshold and the post-processing were all chosen on validation by rules fixed in advance; the test set was used only to report the result.

12How YOLO turns an image into boxes

What happens inside the detector between a 1,120-pixel grid going in and the final Object IDs and boxes coming out. Part of the Milestone 2 lessons: how every photo got its box · the five model runs.

the networkpredictionsinput and filtering

Step by step

  • An image is numbers. A 5x5 grid is 1,120 × 1,120 pixels × 3 colours: about 3.8 million values between 0 and 255.
  • Backbone. Stacked convolutions, small pattern detectors that slide over the image. Early layers find edges and colour changes, middle layers parts and textures, deep layers whole-object evidence. The map is shrunk as it goes deeper, so each position sees a larger area. COCO pretraining supplied this skill; training on the project data taught the 73 objects.
  • Neck. Passes information both ways between the shrunk maps, so every map knows both what is there and where.
  • Heads. Predict on three maps. At every position: four box edges (distances from that position) and a score for each of the 73 objects.
  • Filtering. Keep candidates with confidence of at least 0.10, remove duplicates, then apply the project's rule of one box per 224-pixel cell.

The three maps for a 1,120-pixel input

MapEach position coversPositionsBest for
fine (÷8)8 × 8 px140 × 140 = 19,600small objects
medium (÷16)16 × 16 px70 × 70 = 4,900medium objects
coarse (÷32)32 × 32 px35 × 35 = 1,225large objects
total25,725 candidates

One 224-pixel photo covers 28 × 28 positions on the fine map but only 7 × 7 on the coarse one, which is why very small objects depend on the fine map.

Removing duplicates

Neighbouring positions often detect the same object. YOLOv8 removes the extras afterwards with non-maximum suppression (NMS): keep the highest-scoring box and delete weaker boxes that overlap it. YOLO26 is designed to make one prediction per object, so it does not need NMS. On top of either, the project keeps only the best box in each 224-pixel cell, because a grid cell holds exactly one object.

How training fits in

For each training image, the true boxes decide which positions are responsible for each object. The model is penalised for box error (poor overlap with the true box, measured with IoU) and class error (wrong object scores); each batch of 4 nudges the weights to reduce both, 375 times per epoch.

13Measuring a detector

How every score in the project is built, from one question asked about every box: is this box right? From IoU to precision and recall, AP, mAP and the project's own grid measures.

1. IoU: how well two boxes overlap

IoU (intersection over union) = the area two boxes share ÷ the total area they cover together. 1.0 is a perfect match; 0 means no overlap. Each example below uses a true box of 100 × 100 px (solid) and a predicted box (dashed); the shaded area is what they share.

A box that is only "a bit off" already falls to about 0.67. The third case is the tissue box from the label audit: a box around only the paper, against a true box around the whole tissue box, scores 0.30, below the 0.5 needed to count.

2. When a prediction is correct

A predicted box is correct when it names the right Object ID and its IoU with the true box is at least 0.5. Every box and every true object then falls into one outcome:

OutcomeMeaning
correctright ID, IoU ≥ 0.5
box offright ID, IoU below 0.5
wrong IDa box in the right place naming the wrong object
misseda true object with no box
extraa box where there is no object

3. Precision and recall

Recall = correct ÷ all true objects: of everything that was there, how much was found. Precision = correct ÷ all boxes drawn: of everything claimed, how much was true. The bars show the selected model on the 72 test grids.

The 956 correct objects follow from 1,041 − 16 wrong IDs − 69 misses. The number of boxes drawn (about 1,027) is derived from the precision, so the "about 71" is approximate. Precision and recall pull against each other through the confidence threshold: a lower threshold draws more boxes, finding more objects (recall up) but adding more mistakes (precision down). The project's 0.10 was the balance chosen on validation.

4. AP: one object, every threshold

For one object, sort all its predicted boxes by confidence, walk down the list noting precision and recall after each box, and plot precision against recall. AP (average precision) is the area under that curve, from 0 to 1. AP = 1.0 means every correct box ranked above every wrong one, so the object is handled perfectly at any threshold. The tissue box went from 0.30 to 0.995 after its label rule was fixed.

5. mAP: the average over all 73 objects

ScoreA box counts whenSelected model, test
mAP@0.5IoU ≥ 0.5: found, roughly in place0.947
mAP@0.5:0.95averaged over 10 cut-offs 0.50, 0.55 … 0.95: rewards tight boxes0.875

Each object counts equally in the average, however many photos it has. The gap between the two says the model nearly always finds the object, but its boxes are not always tight; that is why the model was chosen on the stricter score.

6. The project's grid measures

MeasureMeaningTest
Objects foundthe recall: correct objects ÷ all objects91.8%
Grids fully correctevery object right and no extra box34.7% (25 of 72)
95% confidence intervalthe plausible range for the fully-correct rate with only 72 grids23.6–45.8%

One slip spoils a whole grid, so the fully-correct rate falls from 87.5% on 2x2 grids to 7.1% on 5x5, while objects found stays around 90–98% at every size. With 72 grids, each grid moves the rate by about 1.4 points, which is why the interval is wide.

In one sentence

IoU judges one box; precision and recall judge all boxes at one threshold; AP judges one object across every threshold; mAP averages AP over the 73 objects; and the fully-correct rate is the strictest test, a whole grid without a single slip.

15The EYE

Why the EYE was built, how its parts work together, why it judges exactly like the evaluation, how it explains each miss, and what it revealed.

Why it exists

A test score says how often the model is right, not why it fails on a particular object. The EYE shows the model working on a grid, draws every box and explains each object's result in plain words.

How the parts fit together

Everything is one Python file (m2_eye_app.py in Milestone 2) that runs a small local web server; nothing beyond Python and the model needs installing.

It judges exactly like the evaluation

  • Random grids use held-out test photos only, whose true boxes were all checked by a person.
  • It uses the same model, the same confidence threshold, one box per 224-pixel cell, and IoU ≥ 0.5 for "correct".
  • So a miss shown in the EYE is a miss the report counts too.

How it explains a miss

The model produces thousands of candidate boxes, most below the threshold. The final result keeps only the confident ones, but the EYE also looks at the weaker candidates to explain what happened to each true object.

Most of the concrete failures in lesson 14 were found by using the EYE: the missed rotated photo, the pencil case covering 1.3% of its photo, the mouth-guard case at 0.0996, the watch box at IoU 0.37 caused by a partial label, and the card wallet seen on an empty background. In one sentence

The EYE is a one-file local web app that runs the selected detector on held-out, human-checked test photos with exactly the evaluation's rules, and explains every miss in plain words.

Rotating a box

For a 224-pixel photo turned 90° clockwise, a point (x, y) moves to (224 − y, x). A box from (50, 30) to (180, 200) becomes (24, 50) to (194, 180): exact arithmetic, like shifting a box into a grid cell.

SAM cut-outs

SAM (Segment Anything Model) outlines an object pixel by pixel when given a box around it. The resulting mask lifts the object out of its photo so it can be pasted anywhere. The training box stays the person-checked box: the mask only cuts the object out, so SAM never changed a label. A quality gate checked each mask against the agreed box for fill, spill and fit: 6,752 accepted, 133 rejected (1.9%). A sample sheet looked clean: the tissue box whole, the paddle alone, the watch with its strap.

Backgrounds were split into training and test backgrounds, so test scenes use backgrounds the model has never seen. boost's best validation score was 0.880. It is not comparable with Milestone 2's validation scores: the new validation set (292 images) includes rotated grids, scenes and cut-outs and is much harder.

Shared settings

  • Learning rate 0.002 with a cosine schedule: small steps, so fine-tuning adjusts what Run 5 learned instead of overwriting it.
  • Patience 10: stop if validation does not improve for 10 epochs.
  • Mosaic off: the training images are already composites, so stitching four together would only make unrealistic jumbles.
  • On the fly: left–right flips (50%) and light zoom, shift and colour changes.

Why 1,280 px first, then 1,600

The input size is the model's internal magnification: the milestone images stay the same, the model enlarges them before looking and scales its boxes back exactly. At 1,600 px everything is enlarged ×1.43 compared with 1,120, so an object covering 1.1% of its photo grows from about 23 to about 33 pixels. The cost is about 1.56× the pixels of 1,280: much longer training and room for only a batch of 2.

boost used 1,280 because the diagnosis showed small objects caused only about 5 of the 38 upright misses, and 1,600 roughly doubles the training time. boost2 then tested whether more magnification plus the pass-2 labels would pay off.

Working safely

  • Training could resume from the last saved epoch with the same settings, and a finished run was never overwritten by accident.
  • boost2 reused boost's SAM cut-outs and photo cache, and left boost's files untouched.
  • After every phase a fingerprint (hash) check confirmed the submitted Milestone 2 work was unchanged: Run 5's weights, its results file, boxes_master.csv and the original EYE.

How the final model was chosen by a rule sealed in advance, how its settings were chosen on validation, what one look at five test sets showed, and why boost2 was worth trying even though it lost.

1. The rule, sealed before any boost2 result

Written on 13 October 2026 into selection_rule.txt, while boost2 was still training:

boost2 replaces boost if its mAP@0.5:0.95 on the boost2 validation set (292 images, pass-2 labels) is higher than boost's on the same set, each at its own image size. Otherwise boost stays. Thresholds and post-processing are chosen on validation only. Test sets are reported for the selected model and do not influence the choice.

Its SHA-256 fingerprint (C6A67BD9…F8C0) was recorded at once, and the selection script refuses to decide if the file no longer matches: a prediction sealed in a dated envelope.

5. Reading the results

  • Better on every test set and every measure, normal grids included.
  • Rotation largely solved: recall 0.756 → 0.922, wrong IDs down by three quarters.
  • Cut-outs 0.452 → 0.881 reveal that the old model had partly been recognising backgrounds.
  • The honest trade-off: the low grid threshold accepts more doubtful names; on rotated grids boost made 58 wrong IDs with the final settings against 41 at the evaluation's single threshold of 0.40, still far below the old model's 230.

Why it made sense. The diagnosis's "small objects caused about 5 of 38 misses" applied to upright grids, where every photo fills a 224-pixel cell. In the new scenes objects appear at random, often small sizes, and after boost small-object recall was the weakest number left: 0.859 on normal grids, 0.710 rotated, 0.623 scattered, 0.632 cut-outs. More magnification is the textbook remedy. boost2 also carried the pass-2 labels; the forecast was a modest gain and explicitly not guaranteed. The risk was low: boost stayed as the fallback and the sealed rule could only reject a worse model.

What was weak. boost2 changed resolution, labels and batch size (2 instead of 4) at once, so its loss cannot be pinned on 1,600 px alone; a cleaner test would have trained 1,280 px on the pass-2 labels first. It also cost almost twice the training time: 3.47 hours against boost's 1.95, after a batch-4 attempt was abandoned in its first epoch. Still, a negative result is a result: more magnification was not the bottleneck for this model and data.

23COMPOUND: combining the best models

Whether the project's best models could be merged into one better answer, how the experiment was designed so it could fail honestly, and why it did.

1. The idea

Each model had a measured strength: boost on rotation and scenes, the Milestone 2 model on degraded test images, a YOLOv8-s as a different architecture, and the classifier as the best namer. An insect's compound eye merges many small eyes into one picture; COMPOUND tried the same.

2. A design that can fail honestly

Every setting was chosen on four folds of validation and scored on the fifth, from short lists fixed in advance. The rule's text was fixed in the instructions before the run; the file and its fingerprint were written after one-line validation summaries of a discarded first run had been seen, while the code was unchanged from before both runs, and the decision was recorded before any test prediction existed. Writing that down is what makes the result trustworthy.

3. The result

CandidateFully correct (validation)Cut-out recallFalse boxes on backgrounds

4. Why it failed, and what that teaches

  • Combination helps grids and hurts scenes. Fusing boxes merged neighbouring objects in crowded scenes and let weak lone boxes through on empty backgrounds, while recall on degraded grids rose by 7.7 to 13.1 points.
  • Orientation correction defeated itself. It picked the right angle for only 37 of 68 rotated grids and turned 29 of 68 upright grids sideways: boost, trained on rotated photos, is almost equally confident at every angle. The robustness Milestone 3 added removed the signal the trick relied on.
  • An intuition from the test set did not hold on validation: the learned weights favoured Run 3 and boost on poor images, not the Milestone 2 model.
Combining models on grids only would probably pass, but it was suggested by these results on a validation set used four times. Testing it here would be choosing after the fact, so it is left for new data. A negative result, measured this carefully, is still a result.

2. Three lessons that carry beyond this dataset

  1. Pretrained weights decide first. About ten points in Milestone 1, and a 73-class detector on one laptop GPU.
  2. Consistent labels matter more than a better architecture. One rule moved the tissue box from AP 0.30 to 0.995; checking every box was the most valuable step of Milestone 3.
  3. Only decisions made on validation, by rules fixed before the results, make a number worth reporting, including the numbers that say a promising idea did not work.

3. What we would do differently

  • Check every box from the start, not after two rounds of label rules.
  • Change one thing at a time: boost2 changed image size, labels and batch size together, so its result cannot be attributed.
  • Correct test labels without the candidate model's help, or with two independent second opinions.
  • Keep a final test set untouched until the last milestone.
  • Save every output where it can be re-read, and keep the fact sheet up to date as you go.
  • Train for the worst condition explicitly: the photo damage used in Milestone 3 was milder than the degraded test.
